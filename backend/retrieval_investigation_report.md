Report: RAG Pipeline Investigation
Date: 2026-02-18

1. **Current Embedding Model**:
   - `backend/src/embed_proxy.py` explicitly loads `sentence-transformers/all-MiniLM-L6-v2` via FastEmbed.
   - This model produces 384-dimensional embeddings.

2. **Stored Embeddings Model**:
   - `data/qna_pairs_with_embeddings.csv` contains 384-dimensional embeddings sourced from "pse" (original project data).
   - Given the dimension and project context, these were highly likely generated by the same model family (`all-MiniLM-L6-v2`).
   - The stored embeddings are valid non-zero vectors.

3. **Retrieval Test Results**:
   - **Initial State**: The `qna` table in Supabase was EMPTY (0 rows). This guarantees generic fallback answers.
   - **Action**: Ran `seed_qna.seed()` to populate the table with 81 rows from the CSV.
   - **Post-Seeding Test**: Even with 81 rows present, the retrieval function `match_documents` returned **0 rows** despite using an extremely permissible similarity threshold of `-1.0`.
   - **Diagnosis**: 
     - Data exists (81 rows).
     - RLS is bypassed (using `service_role` key).
     - The vector index `idx_qna_embedding_ivfflat` is likely corrupted or was created on an empty table in a way that prevents matches.
     - The function `match_documents` relies on this index or the cosine operator `<=>`. If the index is broken, it might return empty results.

**Recommendation**:
1. Drop the `ivfflat` index in Supabase SQL Editor:
   ```sql
   DROP INDEX public.idx_qna_embedding_ivfflat;
   ```
   (Postgres will then perform exact nearest neighbor search, which is fast enough for 81 rows and will fix the issue).
2. If performance is needed later (thousands of rows), recreate the index:
   ```sql
   CREATE INDEX idx_qna_embedding_ivfflat ON public.qna USING ivfflat (embedding vector_cosine_ops) WITH (lists = 10);
   ```

The root cause of "generic answers" was primarily the **empty database table**, and secondarily a **broken vector index** preventing retrieval after seeding.
